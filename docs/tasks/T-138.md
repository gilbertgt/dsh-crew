## 現行契約（T-138 version: 2）

讀者只需要這一節。每一條都是目前實作的行為，後面那條檢查就是它的守門人；改動任何一條都會讓對應的 case 變紅。

1. **PM 規則分兩層，上限是 `PM_CORE_MAX_BYTES`。** `roles/pm.md` 是 always-loaded core，只放 invariant、路由判斷、硬規則與 `solo` 的兩種訊息形狀；流程、文件儀式、決策紀錄、job ledger、paired shape 與完整硬規則清單在 `roles/playbooks/` 的八個檔案，`host/playbooks.js` 是唯一 manifest（`composePmRules()` 等於 core 加全部 playbook）。
   - 現行上限是 `PM_CORE_MAX_BYTES = 24 KiB`（24,576 bytes，常數與理由在 `host/playbooks.js`），`roles/pm.md` 實際大小約 23 KB。**v1 的 20 KiB 硬限制已不存在**，只在文末的 history 裡當歷史。
   - 他人驗證：`node qa/T-138/case-01-core-and-manifest.mjs`。
2. **PM 用 `crew_playbook` 讀 playbook，不用 `read` 加路徑。** playbook 隨 package 出貨，工作區相對路徑只有在 checkout 裡才成立；索引（`roles/pm.md` 的表格）與 manifest 必須逐字一致，**每個 playbook 自己的 `Read this when:` 也必須與 manifest 逐字一致**，兩邊都檢查。
   - 他人驗證：`node qa/T-138/case-05-playbook-loader.mjs`、`node qa/T-138/case-09-contract-consistency.mjs`。
3. **`crew-flow` 只有 `crew` route 讀（約 95 KB）。** core 給 `direct` 自己的五步流程：`inspect` → `edit` → targeted validation → completion gate → `commit`；`solo` 有自己的五個 bullet。兩者都不引用任何 step number，`crew` 的 bullet 才說「選定本 route 後才讀 `crew-flow`」。security 問題的封閉清單住在 route-neutral 的 `crew-routing` playbook，所以 `direct`／`solo` 不需要為了它打開 flow。
   - 他人驗證：`node qa/T-138/case-02-routes-and-message-shapes.mjs`、`node qa/T-138/case-09-contract-consistency.mjs`。
4. **child persona 是固定四層組裝**：`host/child-policy.js` 的 `CHILD_POLICY_ORDER`（common → shape → role → language）；九個角色檔不再各自重複共用段落，**也沒有任何 `<!-- crew-common -->` marker**（v1 用 marker 定位 common 層，已全部移除）。
   - 他人驗證：`node qa/T-138/case-03-persona-composition.mjs`。
5. **三路由契約**：`direct`（0 個 child、不寫任何文件，commit message 就是紀錄）、`solo`（1 個 `crew_engineer`，至多再加 1 個指名 reviewer）、`crew`（編號流程）。「是否需要 security review」是第二個問題，永不自己移動 route。
   - 他人驗證：`node qa/T-138/case-02-routes-and-message-shapes.mjs`、`node qa/T-137/case-03-security-review-separate-from-route.mjs`。
6. **`solo` 沒有 task row**，也沒有 task table、PRD、ADR、CRD、job folder 或 `state.json`：TaskBrief 是它唯一的契約，acceptance list 就在裡面。blocker 用 `Result`（`status: blocked`）回報，PM 用 `send_message` 回**同一個** continuable engineer，**不先寫任何文件**。
   - 他人驗證：`node qa/T-138/case-06-solo-contract.mjs`、`node qa/T-138/case-09-contract-consistency.mjs`。
7. **`state.json` 只屬 `crew` route**：`direct` 與 `solo` 不建立也不更新它（兩者都沒有 job folder）。`crew` 的 checkpoint、`merge.publishCheck` 與 restart 通知都以它為準。
   - 他人驗證：`node qa/T-138/case-09-contract-consistency.mjs`、`node tools/verify-jobs.mjs`。
8. **bug escalation 依落地的 route 分開記錄**：`direct` → `solo` 先寫 **TaskBrief**，**絕不寫 task row**；`direct`／`solo` → `crew` 才在啟動 crew engineer 前寫 task row；留在 `direct` 的 bug 以 commit message 為完整紀錄。
   - 他人驗證：`node qa/T-138/case-09-contract-consistency.mjs`。
9. **`crew_playbook` 是不可覆寫的 PM-only invariant**：allow list 會把它移除、deny list 會把它聯集回來，只指名它的 `roleAllow` 在 mount 時就被拒絕。
   - 他人驗證：`node qa/T-138/case-08-pm-only-invariant.mjs`。
10. **QA 驗證的是契約本身**：`qa/T-138/` 的 suite 對 shipped prompt 做可執行解析與負向 mutation；因拆家而改變讀取位置的既有 case 改成讀「組裝後的文字」（PM 的 composed rules、child 的 composed persona），斷言是**搬到新契約**，不是放寬。
    - 他人驗證：`bash qa/run-all.sh`。
11. **預算報表只量 always-loaded core 的原始碼大小**：`tools/measure-prompt-budget.mjs` 從兩個 revision 印出 bytes 與行數（精確值）與 `~tokens`（四位元組一 token 的估計），並明文說它不是 live job 的 wall-clock／token A/B，也不預設任何百分比目標。
    - 他人驗證：`node qa/T-138/case-04-ab-measurement.mjs`。
12. **沒有限制 child 數的設定**：`limits.liveAgents` 只管同時醒著的 agent，舊的 `limits.agentsPerJob` 已移除（仍會印一行提示並忽略）；`limits.reviewRounds` 只接受 2。
    - 他人驗證：`node tools/verify-mount.mjs`、`node tools/verify-role-settings.mjs`。

## Migration history（歷史，不是現行需求）

以下每一條都被上面的現行契約取代。留著是為了讓後人知道「為什麼現在是這樣」，**不是**可以照著做的規則；若與現行契約衝突，一律以現行契約為準。

- **item 1**：把 PM 規則拆成 core 與八個 playbook，core 訂為 **≤ 20 KiB**。
- **item 2**：`qa/rule-guard-map.md` 改成一個檔案一個 section，`tools/verify-rule-guard-map.mjs` 支援 `roles/playbooks/<file>.md` 與 `host/child-policy.js` 這兩種新的 section 來源。
- **item 3**：child persona 四層組裝，九個角色檔原本放共用段落的位置留下 `<!-- crew-common -->` marker。
- **item 4**：三路由契約。當時 `solo` 的描述仍帶著「只有一個 task row」，與後來的 v2 相反。
- **item 5**：新增 `qa/T-138/` contract suite，既有 case 改成讀組裝後文字。
- **item 6**：`tools/measure-prompt-budget.mjs` 從兩個 revision 印出 prompt 大小。
- **items 7–8**：既有 41 個 QA folder 與其他 project check 全綠；本次不動 Crew Settings、client boot graph、Git guard、PM write guard 與 model routing。

### v1 → v2（同日追加，items 9–14）

- **item 9：`crew_playbook` 載入工具。** v1 教 PM 用工作區相對路徑 `read roles/playbooks/crew-flow.md`，那只有當 cwd 剛好是 dsh-crew checkout 時才成立。改成唯讀工具 `crew_playbook`（`host/playbook-tool.js`，manifest 由 `host/playbooks.js` 提供，`readPlaybookByName()` 以 `import.meta.url` 解析）。**現行契約第 2 條。**
- **item 10：`solo` 契約落到 child roles。** briefing 明確帶 `route`；`crew_engineer` 與 `crew_security_reviewer` 依 route 分支：`solo` 讀 TaskBrief 與 ReviewBrief，`crew` 讀 PRD 與 task row。**現行契約第 6 條。**
- **item 11：`solo` 不再讀 `crew-flow.md`。** 索引把 `crew-flow` 標成「只有 `crew` 讀」，TaskBrief、blocker、Result、targeted validation 與 commit 的最低規則全部寫進 core。**現行契約第 3 條。**
- **item 12：`CHILD_POLICY_ORDER` 與實際組裝一致。** 舊版靠角色檔裡的 `<!-- crew-common -->` marker 定位 common 層，實際順序與宣稱的四層不符；現在 `composeChildPersona()` 就照 `CHILD_POLICY_ORDER` 串接，**marker 全部移除**。**現行契約第 4 條。**
- **item 13：兩個 `## Hard rules` 同名段落。** core 的改成 `## Always-loaded invariants`，playbook 的改成 `## Full hard-rule reference`。
- **item 14：預算報表的措辭。** 數字改標成 always-loaded PM core 的原始碼大小；core 預算因為 item 11 的實質內容**由 20 KiB 上調到 24 KiB**（`PM_CORE_MAX_BYTES` 常數旁寫了理由）。**20 KiB 已不是規則。**
- **v2 追加的契約清理（無編號）**：`solo` 不再有 task row／task table／ADR／CRD，退掉 `<job-slug>` job folder 與 `state.json`，`artifact paths` 改為可選；`roles/playbooks/crew-routing.md` 只留 route 選擇、security 判斷、角色歸屬與升級，Crew 專用儀式（interview、opening document、change request、milestone review）移回 `crew-flow`／`hard-rules`；`crew-flow.md` 檔頭、`host/playbooks.js` 的 `when` 與 `roles/pm.md` 的索引三處逐字對齊；本輪再把 `hard-rules.md` 的 `solo` blocker／bug escalation／`state.json` 與 core 的 `direct` 流程收乾淨。**全部由現行契約第 3、6、7、8 條與 `qa/T-138/case-09` 取代。**

## 待辦（下一輪，獨立工作）

- **`crew-flow.md` 約 95 KB，而 `crew_playbook` 一次回傳整個檔案。** 單一 tool result 這麼大，目前是靠工具結果的上限去吸收，那是掩蓋而不是解法，本輪**不動**它、也不去調高 pruner 的門檻。方向是依 stage（plan／build／review／finish）把 `crew-flow` 拆成數個按需載入的 playbook，讓一個 `route: crew` 的 job 一次只讀它當前那一段。這是獨立的一件工作，不與本契約修正綁在一起。
- **`solo` 崩潰後無法續作。** 這輪依契約移除了 `solo` 的 job folder 與 `state.json`，所以一個中斷的 `solo` job 沒有東西可恢復；要不要一個 minimal resume state 是下一輪的決定。
- **security 風險清單目前有兩個家。** `crew-routing.md`（route-neutral，`direct`／`solo` 讀這裡）與 `crew-flow.md` 的 step 10b（`crew` 自己那一份，由 `qa/T-137/case-03` 釘住）。兩份措辭目前一致，但同一個封閉清單住在兩個檔案就是漂移的風險，下一步應決定單一住處。
- **`roles/pm.md` 的 push 相關 invariant 仍以 `step 16`／`step 17` 指路**（`qa/T-94`、`qa/T-64` 釘住）。它們是權限規則、不是流程要求，所以本輪未動；若要連編號一起拿掉，得先決定那兩條 case 的斷言搬到哪裡。
